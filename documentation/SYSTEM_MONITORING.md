## 1. Observability Architecture Overview

Cyber Raksha AI incorporates a zero-overhead, in-process observability subsystem built into FastAPI. It tracks API latency percentiles, error rates, per-endpoint throughput, database footprint, and subsystem readiness without requiring third-party SaaS agents or paid APM services.

```
                          ┌───────────────────────────┐
                          │   Incoming HTTP Request   │
                          └─────────────┬─────────────┘
                                        │
                                        ▼
                          ┌───────────────────────────┐
                          │ Observability Middleware  │
                          │ - Starts High-Res Timer   │
                          └─────────────┬─────────────┘
                                        │
                                        ▼
                          ┌───────────────────────────┐
                          │    Core Analysis Route    │
                          └─────────────┬─────────────┘
                                        │
                                        ▼
                          ┌───────────────────────────┐
                          │ Observability Middleware  │
                          │ - Stops Timer             │
                          │ - Records Latency Sample  │
                          │ - Appends X-Response-Time │
                          └─────────────┬─────────────┘
                                        │
                                        ▼
                          ┌───────────────────────────┐
                          │   MetricsTracker Ring     │
                          │ (p50, p95, p99, Errors)   │
                          └───────────────────────────┘
```

## 2. Monitoring API Endpoints

### A. Subsystem Health Status
`GET /api/v1/monitoring/health/detailed`

Returns detailed readiness for all internal platform components:
- **`api_server`**: Basic HTTP listener status.
- **`database`**: Connectivity check, roundtrip latency, and driver status.
- **`ai_models`**: Subsystem statuses for Phishing RF, Communication NLP, and VoiceShield RF.
- **`threat_intelligence`**: Freshness status and active IoC count.
- **`job_worker_pool`**: Active worker threads in `ThreadPoolExecutor`.

**Example Response:**
```json
{
  "status": "HEALTHY",
  "services": {
    "api_server": "HEALTHY",
    "database": {
      "status": "HEALTHY",
      "latency_ms": 1.25,
      "detail": "Relational SQLite engine accessible"

        "communication_nlp_model": "READY",
```

### B. Rolling Performance Metrics
`GET /api/v1/monitoring/metrics`

Calculates live performance indicators over the latest 1,000 requests:
- **`uptime_seconds`**: Total seconds since service startup.
- **`total_requests`** & **`total_errors`**: Cumulative counts.
- **`error_rate_percent`**: Percentage of 4xx and 5xx responses.
- **`latency_ms`**: Minimum, Average, p50 (median), p95, p99, and Maximum latency in milliseconds.
- **`top_endpoints`**: Per-route call counts and average response times.
- **`resource_usage`**: Disk footprint of `cyber_raksha.db` and runtime environment version.

## 3. Response Headers for Distributed Tracing

Every response served through the FastAPI application includes an operational trace header:
```http
X-Response-Time-Ms: 12.45
```
This enables frontend applications, browser extensions, and client diagnostics to monitor API latency directly.

---

## 4. Structured Operational Logging Format

Log entries generated by the platform adhere to standard structured cybersecurity logging conventions:
```
[YYYY-MM-DD HH:MM:SS] [LEVEL] [SUBSYSTEM] Message payload (target, duration_ms, classification)
```
Example:
```
[2026-11-08 00:35:10] [INFO] [DETECTION_SERVICE] Analyzed target URL: 'https://example.com' | Classification: LEGITIMATE | Latency: 14.2ms
[2026-11-08 00:36:20] [WARN] [SECURITY_ALERT] Rate limit exceeded by client IP 192.168.1.45 on endpoint /api/v1/detection/url
```
